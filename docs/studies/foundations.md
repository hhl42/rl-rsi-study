# Foundations: concepts and optional papers

The [study guide](../01-study-plan.md) owns the reading and viewing sequence. This page is a quick reference for distinctions that matter when designing tasks and assessing improvement claims. Use the [survey](../02-survey.md) for fuller explanations and the [glossary](../glossary.md) for terminology.

## What changes during improvement

- **Weights:** numerical parameters learned during training. A weight update can affect later executions without retaining the earlier conversation.
- **Context:** messages, tool results, and other material supplied in the current execution. A useful runbook can improve performance through context without a weight update.
- **Harness:** software that controls tools, context, execution, and recovery. Changing retry logic or tool interfaces changes the system around the model.
- **Persistent memory:** stored information retrieved in later executions. Its contents can change while the model weights and harness remain fixed.
- **Task pool:** available problems and environments. Improving their selection or construction changes what the agent encounters, not necessarily its ability to solve them.

A self-improvement claim should identify which of these changes, how it is evaluated, and what carries across tasks. Better results on the same task after feedback differ from improvement on reserved tasks.

## Why a fixed version can produce different outcomes

A model assigns probabilities to possible next tokens. Sampling can produce different actions from the same weights and context. Tool timing and environment changes can add variation. Different outputs do not by themselves show learning.

Evaluation therefore depends on the attempt budget, output-selection method, and task sample. Success on any of several attempts differs from choosing one successful output, or succeeding on every attempt. The [measurement glossary](../glossary.md#measurements-and-names-in-the-studies) defines the metrics used in our notes.

## What training consumes

Supervised fine-tuning learns from example responses or trajectories. Preference optimization learns from comparisons between outputs. Online RL collects attempts from the current model, scores them, and uses those scores in updates.

These methods place different requirements on task data, execution, and scoring. Training integration requires knowing which tokens were generated by the model and which arrived from tools. A wrong reward can reinforce the wrong behavior. The survey's [worked training step](../02-survey.md#a-worked-training-step) explains this data flow.

## What a task score establishes

A passing grader does not establish that the intended capability was used. Reference success and empty-submission failure leave valid alternatives, shortcuts, leakage, and grader errors unresolved. Conversely, zero passes can reflect a hard task, weak agent, broken environment, or defective grader.

Task quality, downstream improvement, and commercial value are separate questions. The [research experiments](../experiments.md) preserve proposals for investigating them; they are not prerequisites for reading the studies.
